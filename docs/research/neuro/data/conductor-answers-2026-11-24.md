**3. Is the run-1 compressor's evidence card the device contract?** Yes:
- the format is `semantic_compression.rendered_cards`, with a 512-token budget, interned aliases, and the `REST …`
  line always last;
- **one addition from the E2E attack path:** an L1 alert must reach the card as a detection. Without it the
  explainer judges raw flows and says "insufficient". The harness adds `det=behaviour_change[-,sev2,…]` from the L1
  model to the device's top remote peer and its fan-out cards (`e2e_neuro.py`). The device side should emit the
  same;
- connection state maps `S0` and `REJ` to `rst` (counted as failures), and `SF` to `fin`.

**4. Is closed mode part of the contract, and where do the guards run?**
- **Closed mode: yes.** Every gate Neuro passed was measured with `--mode closed` (the per-request enum schema).
  Fidelity claims hold only under the same constraint.
- **Guards:** A, E and G are deterministic and cheap, and all can run **on the device**:
  - A redacts every quoted value in the context;
  - E filters echoes on the answer;
  - G only deletes tokens.

  None needs a model. Rule T: drop (above).

**5. Should the grounding checks become verifier findings, and at what severity?** Run guard G **before** the
verifier; after G, an invented technique id or an unreturned CVE id cannot remain. Suggested statuses:

| Finding | Status |
|---|---|
| CVE id present that no `lookup_exposure` result supplied (only possible if G did not run) | **REJECTED** |
| unknown ATT&CK id (only possible if G did not run) | **REJECTED** |
| G edited the answer | accepted, with the edit recorded in the ledger |
| a service named without its port on the cards (`grounding.service_check`) | **UNVERIFIED**: reported, not fixable by a filter |

`data/attack-ids.json` (ATT&CK 20.1) is the list to mirror; a drift gate like the contract's fits.
