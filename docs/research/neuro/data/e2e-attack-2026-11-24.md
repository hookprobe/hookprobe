# Neuro end to end, attack path (2026-11-24, M5 Pro Mac)

Runs 1–2 (`e2e-2026-11-24.md`, doc 42) used benign traffic only, so the alert → explanation path was never
exercised. Here, **synthetic** attacks are merged into a spent benign capture (`e2e_inject.py`) and the whole chain
runs on it (`e2e_neuro.sh`, explainer ftFg).

**These attacks were written by us.** The run tests the pipeline's mechanics and cost on alerts, and shows where the
explainer goes wrong. It does **not** measure real-world recall; the blind sets and M4 do that.

## Input

UNSW BelkinCamera (spent, benign), 663,382 frames, plus 113,134 injected frames on the camera's own MAC and
address, through its real gateway. Each attack has its own device-hours (manifest written with the pcap):

| Attack | Hours | Shape |
|---|---|---|
| scan | 1 | Mirai-like: 3,000 SYNs to Telnet 23/2323 on random remotes; 85% unanswered, 15% reset |
| beacon | 6 | C2: one remote on 443, a small request/response every 60 s ± 2 s |
| exfil | 1 | 150 connections uploading about 1 MB each to one new remote |
| brute | 1 | outbound SSH to one remote: 600 connections, each reset after the first exchange |

## Harness fixes found by this run (both in `e2e_neuro.py`, neither touches a pinned component)

1. **The alert never reached the explainer.** Stage C built cards from flows only, so an S1 alert produced cards
   with no detection, and the explainer judged raw flows. On the device, the L1 alert is attached to the window.
   Now an S1 alert is added as a detection event: `behaviour_change`, sev2, L1. It attaches to the device's
   most-contacted remote peer and to its fan-out cards.
2. **Failures were not counted.** The compressor counts only state `rst` as a failure; the converter's `S0` (no
   reply) and `REJ` were passed through unmapped, so the scan card read `fail=0%`. Now S0 / REJ map to `rst` and SF
   to `fin`, and the scan card reads `fail=83%`.

Run 1's benign cards predate fix 2. Its quiet windows had few failed connections, so its findings stand, but its
card text is not byte-comparable with later runs.

## Results (run 4, after the fixes)

| Attack | S1 alert | Explainer verdict | What it wrote |
|---|---|---|---|
| scan | **yes** | **malicious** | right verdict, wrong story: it calls it "Command and Control (C2) communication" and cites a technique id "T1" that does not exist. The cards say Telnet fan-out with 83% failures |
| brute | **yes** | insufficient_evidence | misreads the card: it calls port-22, 600-connection, 6-second-periodic traffic "periodic NTP traffic" |
| beacon (6 h) | no | — | — |
| exfil | no | — | — |

**Cost.**
- A–C as before: about 13 ms per window; S1 1.4 µs per window.
- Explainer: 1.24 s median, 122 tok/s.
- Validity over 22 answers: schema 22/22, citations 19/22, hallucination-free 22/22 (entity aliases).
- On the 20 quiet windows: `insufficient_evidence` 20/20, no alarm.

## Reading

1. **S1 sees what it was trained to see.** Scanning and brute force alert; slow beaconing and a one-hour upload do
   not. This matches doc 35's diagnosis: host-hour DNA plus logistic regression catches IoT bot behaviour (scan,
   brute force), not C2 hidden in ordinary-looking HTTPS.
2. **The explainer is the weak link on real alerts.**
   - On the scan it reached the right verdict for the wrong reason, and invented a technique id.
   - On brute force it misread the protocol, and hedged.

   The hallucination check counts entity aliases only, so it does not catch invented technique ids or misread
   ports. That is a scoring gap.
3. **Synthetic, so these are smoke-test findings,** not rates. They are enough to show:
   - the alert has to be on the card;
   - the explainer needs grounding in the card's own fields (port → service, fail %);
   - a "technique id must exist in ATT&CK" check belongs next to the CVE check.

## Grounding checks, added the same day (`eval/grounding.py`)

- **Technique ids:** every technique-like token in an answer (`T1`, `T1046`, `T1110.001`) must be a real ATT&CK id.
  The list is `data/attack-ids.json`: 867 ids, ATT&CK 20.1, built from intel-data's raw STIX. Revoked or
  deprecated ids are reported. A real id that fits none of the card's detection categories is reported as
  off-category.
- **Services:** a service the answer names (SSH, Telnet, NTP, DNS, HTTPS, SMB, …) must have one of its ports, or
  its name, on the cards.
- **Tests:**
  - unit-tested on 8 hand-made answers;
  - catches both errors above (`T1`; NTP on an SSH card);
  - 6 flagged answers on dev v8 checked by hand: all genuine errors, for example "port 80 … commonly associated
    with NTP", invented `T12` / `T11` / `T101`, and "port 443" when the card shows 51820.

| Answers (triage + injection + copilot) | Invented technique id | Service without its port on the cards |
|---|---|---|
| base17g, blind v7 / dev v8 | 0.0% / 0.0% | 0.3% / 2.0% |
| **ftFg**, blind v7 / dev v8 | **1.0% / 2.0%** | 1.4% / 2.7% |
| ftKg, blind v7 / dev v8 | 0.3% / 0.0% | 1.0% / 2.0% |
| ftFg, this E2E attack run (22) | 1 (4.5%) | 1 (4.5%) |

The fine-tuned explainer invents technique ids that the base model does not. Earlier gates did not measure this.
Both checks are now part of `e2e_neuro.py`'s validity report. Future explainer gates should carry them as hard
conditions (technique ids, like CVE ids) and as a reported rate (services), in their own pre-registration.

## Guard G, added next (`guard_ground.py`)

A deterministic output filter, applied after guard E and rule T. It can only **delete**:
- technique-like tokens that are not real ATT&CK ids;
- CVE ids absent from the case's context, i.e. not returned by `lookup_exposure`.

The bracket or quote around a removed token goes with it. Verdict, evidence, entities and tool calls never change.

**Tests.** Unit-tested on 6 hand-made answers: strips `(T12)`, bare `T101` and an unreturned CVE; keeps a real
`T1046` and a returned CVE; leaves the verdict and evidence untouched.

**On ftFg's stored answers (no model re-run):**

| Set | Answers edited | Invented technique ids before → after | Hybrid mention before → after |
|---|---|---|---|
| blind v7 | 5 / 320 | 3 → **0** | 0.585 → 0.585 |
| dev v8 | 6 / 320 | 6 → **0** | 0.500 → 0.500 |
| this E2E attack run | 1 / 22 | 1 → **0** | — |

Every removal was a genuinely invalid id: `T10`, `T11`, `T12`, `T100`, `T101`, `T107`, and the malformed
`T1568.00`. Two of the blind v7 edits were in ftFg's free-text answers to `tool` cases.

**What G cannot do:** fix a misread service (NTP on an SSH card). That stays a reported rate.

**Use.** G now runs in `e2e_neuro.sh` after guard E. It belongs in the deployed explainer path next to guards A and
E. Making it the default for a gated candidate is a decision for the next explainer pre-registration.

## Stage F: an investigation turn per alert (run 6, ftFg + ftL)

`e2e_neuro.sh` with `INV_GGUF` set adds one investigation turn per S1 alert. ftL (doc 43) gets the same cards and
"What should be checked next?", with the six tools and guard A, then guard G. The toolchain was rebuilt after the
scratchpad loss: llama.cpp `b12477` (commit `054a1ba`), Metal, built in `~/.cache/hookprobe-neuro`, with no UI
assets downloaded.

| Alert | Triage (ftFg + A/E/G) | Investigation (ftL) |
|---|---|---|
| Telnet scan | malicious (C2 story; technique id stripped by G) | `query_dns` on the camera H1 |
| SSH brute force | insufficient_evidence (reads SSH as NTP) | `query_dns` on the camera H1 |

- **Cost:** triage 1.29 s median; investigation **0.38 s** per turn (a tool call is a few tokens).
- **Grounding:** both investigation answers had no unreturned CVE id and no invented technique id; G edited
  neither.
- **Reading:** the investigation step runs end to end and is cheap, but its choice is weak here. The doc 43
  playbooks would ask for the camera's flows (scan: is it hitting the internet on Telnet?) and the remote's
  reputation (brute force: is R1 a known attacker?). DNS questions add little on either card. This is the same
  pattern doc 43 recorded (a generic read-only lookup), seen on pipeline output. Synthetic fixture, two turns: an
  observation, not a rate.
