# Neuro end to end, run 1 (2026-11-24, M5 Pro Mac)

**Operator rule:** every Neuro change is followed by an end-to-end test of what it costs and what it delivers.
Harness: `tools/neuro-research/e2e_neuro.sh` + `e2e_neuro.py`. Every stage uses the validated component unchanged.

```
capture (pcap) --A--> device-hour DNA (pcap_to_dna, doc 20 rule) --B--> frozen S1 decision
               --C--> evidence cards (the device's compressor, 512-token budget)
               --D--> explainer ftFg (llama-server, guard A, then guard E + rule T) --> answer
               --E--> lookup_exposure (doc 39 §3.4)
```

**Input.** 4 spent UNSW-IoTraffic captures (BelkinWemoMotionSensor, AwairAirQuality, BelkinCamera, AmazonEcho):
12.2 M frames, 24 devices including their LAN peers. The traffic is benign. No unsealed malicious capture exists on
this machine, so attack-side quality comes from the blind sets, not from here.

## Results

| Stage | Throughput / latency | Memory | Output |
|---|---|---|---|
| **A** capture → DNA | **81,455 frames/s**; 17.4 ms per device-hour window (8,594 windows in 149 s) | peak 1.0 GB (Python, holds every window's events for stage C) | 8,594 windows, 8,295 with ≥ 3 events |
| **B** S1 decision | **1.8 µs per window** | — | **0 alerts** on 8,295 windows (0.000 per device-day) |
| **C** evidence cards | **0.3 ms per window** | — | 20 windows (seeded sample, since S1 raised no alerts): mean 76 tokens, max 108 (bytes/4 estimate) |
| **D** explainer (ftFg Q8_0, 1.7 GB) | **1.34 s median** per answer, p90 1.71 s; prompt 4,340 tok/s, generation 122 tok/s; median prompt 238 tokens | llama-server RSS 3.4 GB; model load 1 s | schema 20/20, citations 19/20, hallucination-free 20/20, guard fallback 0/20 |
| **E** lookup_exposure | **~40 µs per call**; index load 2 ms | — | (timed on the doc 39 P3 branch) |

**Explainer verdicts on the 20 quiet benign windows:** benign 4, insufficient_evidence 16, **suspicious or
malicious 0**. The explainer did not alarm on ordinary traffic. Rule T fired on none (these windows had no
detection cards).

## What it means

1. **The detection path is cheap.** On the Mac, A–C cost about 18 ms per device-hour, so a home of 30 devices costs
   about 0.5 s of CPU per hour. S1 itself is negligible. These are Mac numbers. On-device cost comes from
   HomePods' CM5 metal runs (IDS ns/packet unchanged with Neuro on, #1531; 64-device slot pressure PASS, #1542).
2. **The explainer is the expensive part, and it only runs on alerts.** About 1.3 s and 3.4 GB per answer on the
   Mac GPU. At S1's measured real-home rate (0.10 alerts per device-day, M4), a 30-device home produces about 3
   explanations a day. It does not fit heqk's 4 MiB EL0 window; it stays off-device or companion-tier (doc 30).
3. **Benign traffic produced neither alerts nor alarmist explanations** on this sample.

## Limits of run 1

- **Benign only.** The alert-to-explanation path on real attacks is not exercised. The next runs need an unsealed
  malicious capture (for example a fresh MCFP or CICIoT2023 file registered for *testing*, not as a sealed
  holdout) or synthetic attack traffic replayed into a benign capture.
- **Flow events only** at stage C. `pcap_to_dna` keeps no DNS questions, so DNS cards are missing.
- **Token counts are estimates** (bytes/4); `NEURO_LLAMA_TOKENIZE` / `NEURO_VOCAB` give exact counts.
- **Mac numbers,** not CM5.
