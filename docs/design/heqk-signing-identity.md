# Design note — heqk boot-signing ↔ hookprobe-os release-identity integration

**Status:** DESIGN ONLY — Amber (crosses the trust boundary; operator + security-auditor review
required before any implementation). No signing code, key material, or trust store touched by
this note. Nothing here has been committed.
**Author:** release-engineer, 2026-07-25.
**Scope:** Track C / Milestone M1 deliverable #2, `docs/BuildPlan.md` line 166: *"merge
hookprobe-os hybrid ML-DSA-65+Ed25519 release key ↔ heqk `hboot` boot signing; built under the
hookprobe-os build/release identity (`builder/make-cm5-heqk-image.sh`)."*
**Relates to:** [ADR 0002](../adr/0002-crypto-agility-pqc.md) §3/§5, [ADR 0043](../adr/0043-heqk-microkernel-substrate.md) D4, [ADR 0044](../adr/0044-zero-linux-rpi-native-cm5.md), [ADR 0045](../adr/0045-default-dev-test-credentials.md) D6, [ADR 0046](../adr/0046-github-migration-and-key-custody.md) D4, [ADR 0016](../adr/0016-artifact-hash-signing.md)/[0017](../adr/0017-authenticated-aot-cache.md).

## 0. Headline honesty finding (read this first)

**Every doc that names heqk's boot-signing algorithm as "ML-DSA-65" is factually wrong.** heqk's
`hboot` implements **Ed25519 + SLH-DSA-SHA2-128s (FIPS 205)**, not ML-DSA-65 (FIPS 204). This is
unambiguous in the source:

- `~/heqk-sign/Cargo.toml` (the boot signer's own package manifest, **not tracked in this repo at
  all** — see §1): `description = "HEQK secure-boot signer: hybrid ed25519 + SLH-DSA (FIPS 205)"`.
- `~/heqk-sign/src/main.rs::sign()` signs with `fips205::slh_dsa_sha2_128s`, not `ml_dsa`.
- `kernel/heqk/hboot/src/main.rs:227`: `// Post-quantum: SLH-DSA-SHA2-128s (FIPS 205) — hash-based, quantum-safe.`
- `kernel/heqk/hboot/src/trusted_keys.rs:11`: `pub const SLHDSA_PUBKEY: [u8; 32]`, generated by
  `heqk-sign keygen` — a 32-byte SLH-DSA public key and a 7856-byte signature
  (`mkimage-hboot.sh:11 SLHDSA_SIG_LEN=7856`) are the FIPS 205 SLH-DSA-128s parameter set; ML-DSA-65
  (FIPS 204) has a 1952-byte public key and a 3309-byte signature — structurally impossible to
  confuse with what's actually embedded.

Yet **`docs/BuildPlan.md`:166, `kernel/heqk/PRODUCTION_READINESS.md`:247, ADR 0043 D4 (line 54),
and ADR 0002's heqk coupling note (line 128) all say "ML-DSA-65"** when describing heqk's boot
signing. This is not a nitpick — it changes the actual "merge" design (§2) and the CBOM's
crypto-posture claims (ADR 0002 §4) if left uncorrected. **Recommendation:** these four locations
get corrected to "Ed25519 + SLH-DSA (FIPS 205)" as a follow-up doc-honesty pass (product-steward +
os-architect), same discipline as the 2026-07-05 F5 CBOM honesty pass. This note uses the
**correct** algorithm throughout below.

A second, smaller honesty point in the other direction: **ADR 0002 §3's `boot_signing: "lms"
⏳ Roadmap — no code, "** is also stale for the heqk tier — there IS working, QEMU-validated boot
signing code today (`[HBoot-AB] PASS` in `validate.sh`, confirmed by an actual run of this repo's
gate, see the build-heqk.yml work this note follows), it is just SLH-DSA, not LMS, and it is
UEFI-tier LMS that remains genuinely roadmap. §2 below recommends how to update ADR 0002 to say
this precisely rather than either over- or under-claiming.

## 1. Reality map — the two signing worlds, side by side

| | **heqk boot image** (`hboot` + kernel) | **hookprobe-os modules/release** |
|---|---|---|
| **What's signed** | The combined `hboot` (fixed 2 MiB slot) + kernel payload flat binary that becomes `heqk8.img`/`heqk8-b.img` | Each module's `module.yaml` digest (`module_digest`), and (ADR 0016) each declared artifact's payload bytes; generalized (ADR 0024) to arbitrary artifacts (VEX/SBOM/CBOM) via `dev_sign_artifact_hybrid` |
| **Signed message** | `SHA-256( LE64(svn) \|\| SHA-256(kernel payload) )` — SVN is bound INTO the signed message (`~/heqk-sign/src/main.rs::signed_message`, mirrored in `hboot/src/main.rs:206-209`) so a version can't be edited post-hoc to dodge the anti-rollback floor | `SHA-256(module.yaml bytes)` (or artifact-file bytes for the ADR 0016/0024 legs) |
| **Algorithm(s)** | **Ed25519** (classical) **+ SLH-DSA-SHA2-128s** (FIPS 205, hash-based PQC) — BOTH required, hybrid, fail-closed (`hboot/src/main.rs:234-238`) | **Ed25519** (classical) **+ ML-DSA-65** (FIPS 204, lattice-based PQC) — BOTH required for a hybrid suite, fail-closed anti-downgrade (`module_sig.rs::verify_module_for_suite`, `ADR 0002 §3`) |
| **Signing tool** | `heqk-sign` — a standalone Rust CLI (`ed25519-compact` + `fips205` crates) that lives **at `~/heqk-sign` on this dev box only — NOT in `kernel/heqk/`, NOT in this repo's git history at all** (confirmed: `find kernel/heqk -iname '*heqk-sign*'` returns nothing but doc/comment references; the actual `Cargo.toml`/`src/main.rs`/`keys/` are under the operator's `$HOME`) | `hookprobe-supervisor --sign-modules <keyfile> --trust <dir>` (`builder/sign-release.sh`), backed by `crates/hookprobe-manifest/src/module_sig.rs` — fully in-tree, in the Rust workspace |
| **Key material format** | `ed25519.sk`/`.pk` = raw `ed25519-compact` bytes (64B/32B, an "expanded" secret-key format); `slhdsa.sk`/`.pk` = raw FIPS-205 `SK_LEN`/`PK_LEN` bytes. | **Invoked from** | `kernel/heqk/cm5-boot/mkimage-hboot.sh` → `builder/make-cm5-heqk-image.sh` (M1 seam) | `builder/sign-release.sh` → `builder/release-pass.sh` gate |
| **Dev vs prod key** | Dev only, currently: `~/heqk-sign/keys/*` generated once by `heqk-sign keygen` (2026-07-21). Prod: HSM/CI-secrets custody (ADR 0002 §5, ADR 0046 D4) |
| **Verified by / where** | `hboot/src/main.rs` at EL2, power-on, against `hboot/src/trusted_keys.rs`'s **compile-time-embedded** public keys (never read from the image — "else an attacker could swap key + signature together", `trusted_keys.rs:2-3`) | The supervisor at module-load time, against `builder/trust/{release.pub,release-mldsa.pub}` baked into the RO rootfs image (`modules/.trust/` mirrors it for the dev tree) |
| **Anti-rollback / SVN** | Real: `hboot/src/rollback.rs` — `effective_floor() = max(COMPILE_FLOOR=1, EXPECTED_MIN_HW_FLOOR, live BCM2712-OTP-block-3 thermometer)`, fail-closed on an unreadable OTP read (never drops to 0). `advance_floor` (irreversible fuse-blow) is coded but **"NEVER called from the boot path; only an explicit operator action"** — genuinely not yet wired into any release process (`rollback.rs:120-154`, `PRODUCTION_READINESS.md` PH3: "SEC-6 remains… lives in the metal bring-up batch, not build-blind") | No equivalent SVN/floor concept — module signing has no anti-rollback primitive at all; a re-signed OLDER module verifies exactly like a newer one. (Out of scope for this note, but worth flagging: the module-signing side has nothing to learn from here yet, but the CONCEPT is real and metal-proven on the boot side.) |

| **Maturity, honestly** | Boot chain: real, QEMU-green, **single-metal-run-validated**. Signing pipeline: real, but **dev-keyed only**, key material lives outside version control on one operator's machine, no rotation/revocation story, hardware SVN floor coded-but-unprovisioned. **Not** production-ready as-is — `PRODUCTION_READINESS.md` says so explicitly (PH4, "blocked on a user decision") | Module signing: real, fail-closed, hybrid, **validated on real Pi4 silicon** (10/10 modules verified→running, per project memory), dev key clearly gitignored/documented as non-production. Prod custody model (HSM/CI-secrets, cosign-keyless for images) is decided (ADR 0002 §5, ADR 0046 D4) even though not yet exercised end-to-end |

**Where they align:** both are genuinely **hybrid** (classical + PQC, both legs required,
fail-closed, no silent downgrade) — same *philosophy*, independently arrived at. Both keep the
signing/private key off the verifying device (heqk: `~/heqk-sign`; hookprobe-os: release
pipeline/HSM) and only bake in a **public** key at build time.

**Where they differ, concretely:** (1) different PQC algorithm families entirely (SLH-DSA
hash-based vs ML-DSA-65 lattice-based — see §2 for why this is arguably good, not a defect to
fix); (2) different tools, different repos-of-record (heqk-sign isn't even in this monorepo);
(3) different key-material serialization conventions; (4) heqk's boot signing binds an SVN
anti-rollback floor into the signed message — module signing has no equivalent; (5) heqk verifies
once, at power-on, against compiled-in keys with zero runtime trust-store lookup; module signing
verifies per-load against a filesystem trust directory that can (in principle) be updated without
a full reflash.

## 2. The core decision — one trust root, but NOT one key

**Recommendation: distinct-but-co-rooted.** Do **not** make heqk's boot key literally the same
keypair as either the module-signing Ed25519 or ML-DSA-65 leg. Do unify **custody, provenance, and
release-identity binding** — one governed pipeline mints, rotates, and publishes both, and one
release record ties a boot-image SVN + module-set version together — but the key *material* stays
separate per domain.

**Security rationale:**

1. **Blast-radius separation.** The boot key is HBoot's root of trust — compromise means an
   attacker can sign an arbitrary kernel that boots on real hardware, permanently (short of a
   fleet-wide `hboot`/OTP-floor rotation). The module-signing key gates individual Wasm/native
   payloads at userspace load time — a much larger, more automation-touched surface (every module
   release, potentially CI-triggered). Reusing one keypair for both means a module-signing-key leak
   (the more exposed of the two) becomes a boot-root-of-trust compromise. This is exactly the
   reasoning ADR 0002 §5 already applies to keeping image-signing (cosign-keyless), module-signing
   (HSM), and future firmware-signing (HSM+state) as separate custody lines — extend the same
   logic to heqk's boot key rather than special-casing it.
2. **Different rotation cadences.** A module release can happen many times a week; rotating that
   key is cheap (re-sign, republish `builder/trust/`). Rotating the boot key means bumping
   `hboot/src/trusted_keys.rs`, rebuilding + re-signing `hboot` itself, and (once the OTP floor is
   provisioned) potentially an irreversible fuse-based SVN advance across the fleet — a much rarer,
   higher-ceremony event. Coupling them forces the boot key to rotate on the module cadence (bad)
   or the module key to freeze on the boot cadence (also bad).
3. **Algorithm diversification is a legitimate hybrid-PQC argument, not an inconsistency to
   "fix".** ADR 0002's own stated rationale for hybrid signing is "an attacker must break BOTH …
   defends against future quantum attacks AND against immaturity bugs in young PQC
   implementations" (§3). heqk's SLH-DSA choice for boot signing and hookprobe-os's ML-DSA-65
   choice for module signing are **different PQC primitive families** (hash-based vs
   lattice-based). If ML-DSA (comparatively newer, lattice-based, more open cryptanalytic
   attack surface historically) ever had a structural break, the boot chain — signed with the much
   more conservative, decades-pedigreed hash-based SLH-DSA — would be unaffected, and vice versa.
   Recommend **keeping this diversification deliberately**, not "fixing" it into one shared
   algorithm, and documenting it as intentional (currently it reads as an accident/doc error
   because every doc claims they're both ML-DSA-65 — §0).
4. **SLH-DSA is actually the BETTER boot-signing choice than ADR 0002's own original plan.**
   ADR 0002 §5 names "reusing a one-time leaf index" (LMS/XMSS, SP 800-208 stateful hash-based
   signatures) as **"the single biggest PQC footgun"**. heqk's `hboot` already sidesteps that
   entirely by using **SLH-DSA — a *stateless* hash-based scheme** (FIPS 205), which has no
   leaf-index state to manage, back up, or catastrophically desynchronize. This is a strictly safer
   choice for an on-device boot root of trust than LMS/XMSS would have been, and it's already
   built and QEMU-validated. **ADR 0002 §3's `boot_signing: "lms"` roadmap row should be updated**
   to reflect this — recommend something like: `boot_signing: ["ed25519", "slh-dsa-sha2-128s"]`
   marked **✅ Implemented (heqk/CM5 tier only)**, with the UEFI-tier boot signing (no bootc/OCI
   measured-boot chain exists) staying **⏳ Roadmap**, and §5's custody-design language extended
   to note SLH-DSA's statelessness as a documented reason it needed less custody ceremony than
   LMS/XMSS would have. This is an **os-architect + security-auditor decision** (ADR-editing is
   Amber), not something this note performs.

**What "the two trust chains merge" (ADR 0043 D4) should mean, concretely**, given the above:
- **One release-identity record** (new — proposed in §4) that names, per hookprobe-os release
  version: which module Ed25519/ML-DSA-65 pubkeys are trusted, which heqk boot Ed25519/SLH-DSA
  pubkeys are trusted, and which SVN floor is expected — published together, versioned together,
  in the same `builder/trust/` publishing step.
- **One custody process** (HSM/CI-secrets/operator keystore, ADR 0046 D4) holding all four private
  keys (module-Ed25519, module-ML-DSA-65, boot-Ed25519, boot-SLH-DSA) as **separate objects**
  under the same access-control/rotation/audit regime — not literally the same bytes.
- **One publishing convention**: `builder/trust/` (or a heqk-specific subdirectory under it) is the
  single place a device/image ever reads a public key from, for either chain.

## 3. The integration mechanism — how the identity should flow into `make-cm5-heqk-image.sh`

**Not** "heqk-sign consumes `builder/release.key*` directly" — that's wrong on two independent
grounds: (a) §2's blast-radius argument says it *shouldn't*, and (b) it's not even mechanically
possible without a lossy/confusing conversion — `builder/release.key.mldsa` is an **ML-DSA-65**
seed, and heqk-sign's PQC leg is **SLH-DSA**; there is no such thing as "the same PQC key" across
two different algorithms. Even the Ed25519 legs use different on-disk encodings (hex 32-byte seed
vs `ed25519-compact`'s 64-byte expanded secret-key format) — bridgeable in principle, but
undesirable per §2 even if it were the same algorithm on both sides.

**Proposed mechanism instead:**

1. **A parallel, purpose-named keydir**, not a reuse of `builder/release.key*`. e.g.
   `builder/heqk-keys/` (gitignored, same treatment as `builder/release.key*` today — ADR 0046's
   `.gitignore` already fences `builder/release.key*`; extend the same pattern) holding
   `ed25519.{sk,pk}` + `slhdsa.{sk,pk}` in heqk-sign's expected raw-binary layout.
2. **`make-cm5-heqk-image.sh` sets `KEYDIR`/`SIGNER` explicitly** before invoking
   `mkimage-hboot.sh`, instead of relying on that script's own `$HOME/heqk-sign` defaults
   (`cm5-boot/mkimage-hboot.sh:12-13`). Today `make-cm5-heqk-image.sh` sets **neither** — it
   silently inherits whatever's on the operator's `$HOME`, which is the concrete gap this
   milestone closes (§4 gives the minimal fix).
3. **`heqk-sign` itself moves into version control** — currently it isn't anywhere in this repo
   (§1), which is its own reproducibility gap independent of the identity question ("a release you
   can't rebuild is a liability", release-engineer canon). Recommend vendoring its source into
   `kernel/heqk/tools/heqk-sign/` as its own small `[workspace]` member excluded from the
   `no_std`/`build-std` kernel build the same way the root `Cargo.toml` already excludes
   `kernel/heqk` itself — a host-only Rust binary, ordinary std, no bare-metal constraints. This is
   a **repo-hygiene/reproducibility action, not a trust-boundary action** (moving source, not
   keys) and could land ahead of or alongside the identity-merge work.
4. **Dev-vs-prod split, mirroring the module-signing model exactly:**
   - **Dev:** a deterministic dev keydir (same spirit as `load_or_create_release_key`'s
     SHA-256-seeded determinism), generated by a new small script, gitignored, clearly commented
     "DEV ONLY — never for a release image" — same posture `builder/release.key` already has
     (ADR 0046's Note). This is explicitly **not** an ADR 0045 concern (ADR 0045 governs *login
     credentials*, not signing keys — ADR 0045 D6 says so directly: *"Signing keys… are out of
     scope here and governed by ADR 0016/0002/0046"*) but ADR 0045 D6's closing principle still
     applies in spirit: *"a default key is never acceptable"* in a release — so this dev keydir
     needs the same release-exclusion enforcement §5 item 5 below describes, not a credential gate.
   - **Prod:** `KEYDIR`/`SIGNER` point at operator/CI-provisioned material under the ADR 0046 D4
     custody model (CI secrets / operator keystore) — the **same custody class** as the existing
     module ML-DSA-65/Ed25519 HSM keys, but as distinct key objects (§2).
5. **The cosign-keyless tension, flagged explicitly (this is real, not hypothetical):** image
   signing's production answer is cosign-**keyless** OIDC (ADR 0002 §3, ADR 0046 D4) — an
   ephemeral Fulcio-issued certificate bound to a CI identity, no long-lived private key anywhere.
   That model **cannot** apply to heqk boot signing. `heqk-sign sign` needs actual local private-key
   bytes in memory at sign time (`SecretKey::from_slice`, `PrivateKey::try_from_bytes`), and HBoot
   verifies against **constant public keys compiled into the boot binary at build time**
   (`trusted_keys.rs`) — there is no live network, no OIDC identity, no online CA available at
   device power-on to validate an ephemeral cert against. So **the production heqk boot key must be
   a real, long-lived (ceremony-rotated) HSM/KMS-held key**, structurally identical in custody
   terms to the module ML-DSA-65/Ed25519 keys (ADR 0002 §5's design — release pipeline/HSM,
   monotonic state management once the SVN floor is truly hardware-backed), **not** cosign-keyless.
   This should be stated as fact in whatever ADR eventually formalizes this (ADR 0043 D4 currently
   implies image-signing's keyless model might extend here; it structurally cannot).

## 4. Minimal first implementation step (proposed — NOT implemented here)

The smallest change that makes `make-cm5-heqk-image.sh` build+sign heqk **under an explicit
hookprobe-os identity** rather than an implicit personal-`$HOME` fallback, without touching any
cryptographic code:

1. Add `HEQK_KEYDIR="${HEQK_KEYDIR:-$ROOT/builder/heqk-keys}"` to `make-cm5-heqk-image.sh`, and
   pass it through as `KEYDIR="$HEQK_KEYDIR" SIGNER="$HEQK_SIGNER" ./cm5-boot/mkimage-hboot.sh …`
   (both env vars `mkimage-hboot.sh` already reads — no change needed there).
2. **Fail closed** if `$HEQK_KEYDIR` doesn't contain all four expected key files
   (`ed25519.{sk,pk}`, `slhdsa.{sk,pk}`) — a clear `FATAL:` message, mirroring the script's
   existing Cargo.toml/rust-toolchain.toml precondition style — rather than silently falling
   through to `mkimage-hboot.sh`'s own `$HOME/heqk-sign/keys` default (today's behavior, which is
   what makes the current pipeline non-reproducible off this one operator's machine).
3. A new, small `builder/gen-heqk-dev-keys.sh` (dev/CI rehearsal only, clearly commented,
   deterministic seed, gitignored output) provisions `builder/heqk-keys/` for local/CI builds —
   parallel to how `builder/release.key` is silently created on first run of `sign-release.sh`
   today, but explicit here rather than implicit, since a boot key is higher-stakes (§2).
   Production sets `HEQK_KEYDIR` to an operator/CI-provisioned path instead; this script never
   runs in that path.
4. **`heqk-sign` gets vendored into `kernel/heqk/tools/heqk-sign/`** (§3 point 3) so
   `make-cm5-heqk-image.sh` can `cargo build --release` it from a known, version-controlled
   location instead of assuming a pre-built `~/heqk-sign/target/release/heqk-sign` binary exists.

**Acceptance test for this step:**
- *Positive:* `builder/gen-heqk-dev-keys.sh builder/heqk-keys && builder/make-cm5-heqk-image.sh`
  completes, produces `builder/generated/cm5-heqk/heqk8.img`, and
  `heqk-sign verify builder/heqk-keys <kernel.bin> <svn> <floor> <ed.sig> <pq.sig>` (the existing
  `verify` subcommand — mirrors HBoot's exact accept/reject logic per its own doc comment,
  `~/heqk-sign/src/main.rs:353`) exits 0 against the same keydir's public keys.
- *Negative:* running `builder/make-cm5-heqk-image.sh` with **no** `HEQK_KEYDIR` set and **no**
  `builder/heqk-keys/` present must **abort with a clear error** — not silently fall back to
  `$HOME/heqk-sign` (today's behavior) and not silently produce an unsigned/garbage image. This is
  the regression test that actually proves "built under the hookprobe-os identity" rather than
  "built under whatever happens to be on this laptop."
- Both checks are pure plumbing + a new gitignored key-material convention — **zero changes to any
  cryptographic function body**, in `heqk-sign`, `hboot`, or `module_sig.rs`.

## 5. Security decisions needing security-auditor sign-off (before any of §3/§4 is implemented)

1. **Trust-root topology.** Confirm the §2 recommendation (distinct-but-co-rooted keys, shared
   custody process, NOT shared key material) is the intended reading of ADR 0043 D4's "the two
   trust chains merge, they do not duplicate" — as written, that phrase is ambiguous between "one
   governed process" (this note's reading) and "one literal key" (a plausible but, per §2,
   actively worse reading).
2. **Key custody for the new boot-signing production keys.** Who holds the production
   `ed25519.sk`/`slhdsa.sk` for heqk boot signing — same HSM as the module ML-DSA-65/Ed25519 keys,
   a separate HSM partition, or a separate device entirely? What's the rotation/backup/recovery
   ceremony? (A lost boot-signing key with no backup means no future signed heqk image can ever
   boot on fleet devices already holding the old `trusted_keys.rs` — this is a worse failure mode
   than losing a module-signing key, which only stops NEW module releases.)
3. **`heqk-sign` supply-chain review.** Its dependencies (`ed25519-compact`, `fips205`, `sha2`)
   need the same SBOM/license/version-pinning bar as everything else in this repo before it's
   trusted to sign a production boot image — it currently isn't even in version control (§1/§3).
4. **Anti-rollback (SVN) hardware-floor provisioning cadence.** `advance_floor` is coded but
   deliberately never auto-invoked (`rollback.rs:120-154`); no hookprobe-os release process
   currently calls it. Decide: does every heqk release bump SVN? Does the hardware floor advance
   on every release, or only on releases that fix a boot-chain vulnerability (ADR 0002 §5's
   "advancing = release that fixes a vulnerability you never want rolled back past" framing,
   already in `rollback.rs:24-25`'s own doc comment for `COMPILE_FLOOR`)? This is a policy decision
   this note surfaces but does not make.
5. **Dev-key-never-in-prod-image enforcement, extended to heqk.** ADR 0045 D2 already mandates a
   release-blocking grep for debug login credentials in the assembled rootfs/image. Recommend the
   same discipline extended to heqk: a release-build assertion that `hboot`'s compiled-in
   `trusted_keys::{ED25519_PUBKEY,SLHDSA_PUBKEY}` do NOT match the known dev keydir's fingerprint
   (the ones currently in `kernel/heqk/hboot/src/trusted_keys.rs`, generated 2026-07-21, are — per
   `PRODUCTION_READINESS.md`'s own PH4 note — the dev signer's keys and must never ship in a
   production image as-is).
6. **ADR 0002 doc-correction sign-off** (§0/§2): updating `boot_signing` from `"lms" (roadmap)` to
   an accurate implemented/roadmap split (heqk tier: Ed25519+SLH-DSA implemented; UEFI tier: still
   roadmap), and correcting the "ML-DSA-65" mislabel in ADR 0002's coupling note, ADR 0043 D4, and
   `PRODUCTION_READINESS.md`. Documentation-only, but it feeds directly into what the CBOM is
   allowed to claim (ADR 0002 §4's `hookprobe:status` honesty bar).
7. **SLH-DSA parameter-set choice review.** `heqk-sign` uses `slh_dsa_sha2_128s` (small/slow) for
   boot-image signatures and `slh_dsa_sha2_128f` (fast/larger) for the separate Attestation Key —
   confirm this split is a deliberate, reviewed security-level choice for a long-lived boot root of
   trust, not simply whichever parameter set was convenient during heqk's own bring-up.

---

## Summary

**Recommendation in one paragraph:** keep heqk's boot-signing key (Ed25519 + SLH-DSA) and
hookprobe-os's module-signing key (Ed25519 + ML-DSA-65) as **cryptographically distinct keypairs**
— reusing one key across both domains would collapse two different threat models (boot root of
trust vs. per-module payload gate) into one blast radius, and the algorithm families already
differ for a legitimate hybrid-diversification reason worth keeping. "Merge the trust chains"
should mean **one governed custody/rotation/publishing process** (ADR 0046 D4's HSM/CI-secrets
model, extended to cover the boot keys as additional objects) and **one release-identity record**
binding a boot-image SVN to a module-signing epoch — not one shared key. Production boot signing
cannot use cosign-keyless (no online CA at device power-on); it needs the same HSM custody as
module signing. The concrete first step is pure plumbing (`HEQK_KEYDIR` env + fail-closed
precondition + vendoring `heqk-sign` into the repo) with zero cryptographic code changes, gated on
security-auditor sign-off of the seven items in §5.
