# A-03: one off-subnet connection wedges Mission Control (CM5, 2026-11-14)

Found by the Pi session's LAN assessment (`docs/security/pi4-assessment.md`, finding A-03, High).
Root cause, fix and verification on the bench CM5 (fortress port-4 bench, management VLAN 200).

## Symptom

During the assessment, Mission Control on the management address (192.168.200.146) stopped answering
TCP on both :80 and :443. Ping still worked. It stayed dead until a power cycle. The management policy
dropped nothing (`drop … mgmt=0`), and frames kept reaching the device.

## Bisection

| Step | Result |
|---|---|
| Fresh boot, connect scan of ports 1–10000 (`nmap -sT -T4`) from fortress | MC healthy throughout: the scan is not the trigger |
| ONE `curl` from the Pi's Wi-Fi client to `https://192.168.200.146/` (14:51:04) | MC dead from 14:51:26 |
| Diagnostic image (`[P11-AP3 mc]` line: frames handed to the MC node, IDS drops, node TX, every TCP slot's state), same single probe (15:08:11) | 15:08:22 one HTTPS slot stuck in SYN-RECEIVED; 15:08:46 **all 16 HTTP slots FIN-WAIT, all 8 HTTPS slots SYN-RECEIVED**, node TX frozen (`node->mgmt ok` stuck at 87 while `mgmt->node` kept rising), 0 gated, 0 lost |
| ONE `curl --interface 10.200.0.1` from fortress (a routed source, no Wi-Fi involved, 15:19:11) | MC dead from 15:19:57 |

## Root cause

- The Mission Control node (smoltcp) runs with a static default gateway equal to its OWN AP address
  (10.99.0.1). That address is only a stand-in: the host re-addresses every node frame.
- A reply to any source outside the node's two subnets therefore needs a neighbour entry for that
  gateway. Such sources include:
  - a routed admin;
  - an AP client's packet NATed to the device's WAN address (10.100.0.135) and routed back by the
    upstream router;
  - a spoofed source.
- smoltcp asks "who-has 10.99.0.1 tell 10.99.0.1". `mcmgmt::route` only answered management-side ARP
  locally, so the request went to Wi-Fi and nobody answered.
- The never-resolving neighbour kept smoltcp's shared one-second ARP rate limit busy. The real peers'
  cache entries expired behind it, and every connection stalled waiting for a neighbour until reboot.

## Fix (branch `fix/mc-mgmt-wedge`)

1. **Root cause.** `mcmgmt::route` answers the node's who-has for its own address locally (sender IP ==
   target IP), with or without a management interface. Off-subnet replies now leave by the host's normal
   routing. `[P-mcmgmt]` adds the row.
2. **Defence in depth.** `apcore::forward4` refuses a client packet addressed to one of the device's own
   addresses (management or WAN) with a TCP RST or ICMP admin-prohibited, instead of routing it out to
   come back as a hairpin. It is counted in `to_self_refused`.
3. **Detection attribution.** Rule 1200113 had named the management address itself as a port scanner.
   - An RST or SYN-ACK *to* one of the device's own addresses no longer credits the device as a prober.
   - Frames *from* the device never get a scan verdict.
   - The slow tier counts only an RST that answers an outstanding SYN probe. A client abort RST answers
     none.
   - `[P8-flow]` adds the A-03 rows.
4. **Diagnostics.** `[P11-AP3 mc]` is printed on the management beat.
