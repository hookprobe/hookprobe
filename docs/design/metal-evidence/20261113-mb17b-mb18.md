## Shield row: a lost answer, not a policy or enrollment fault

MB18 was built to test the suspicion that enrolling the owner key (Phase 0) stops the factory Shield list from
applying. It does not:

- Every boot after enrollment logs `[SHIELD] v2: 8 blocked + 0 allowed domains | BLOCK.TXT loaded … (operator signature OK)`.
- In the failing lan2 run the device **counted the query as blocked**:
  `[SHIELD] list=8 … queries=2 blocked=1 … last_blocked=example.org from 10.99.0.10` (the Pi).
- The Pi's single `dig +time=3 +tries=1` got **no reply at all** (no status line), not a resolved address.
- The rule 126 row (TLS to example.org with DNS bypassed via a pinned IP, flagged `shield_bypass`) passed in the same
  run, so the block list was in force.

So the NXDOMAIN answer was lost between the device and the Pi in both runs. Both lost answers came at the first
blocked query after the Pi rejoined from a reboot (Phase 0 ends with a reboot), and neither was retried. #1107 makes
the check try up to 3 times and print every lost try, so it passes only on a real NXDOMAIN and the loss stays in the
log. **Open:** whether the first answer after a rejoin is lost on the device side (Wi-Fi TX of the reply) or on the
air. Next batch: log per try; if the loss recurs, capture on the Pi.
