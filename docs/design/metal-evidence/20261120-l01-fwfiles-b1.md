## 4c / 4d / 4e in QEMU — `os/kernel/tools/fwfiles-fat-cases.sh` on the am22F disk image

The read-only check kernel (the one the image factory boots) against copies of the image with the boot partition
changed by mtools. The device's own MBR + FAT code and the pins of the tree decide; `[P-fwfiles-fat]` prints what the
boot load would report. The boot load and this phase share one reader (`fwfiles::stream_file`); the boot load then
verifies the copy in memory, the phase hashes while reading.

Two checks failed in the batch and were run again:

- **Bench baseline** — `FAIL — generation 1 not in force` on the first run. A full flash wipes the enrolled owner signing key
  and the baseline script did not enrol it, so its bundle was refused. Later in the batch the key was enrolled (the phase-0
  check does it) and the baseline then passed: `PASS — generation 1`. The script now enrols the key itself.
- **Claims C5, "10 spaced bus faults: every outage < 2000 ms"** — worst 2188 ms in the batch run (one fault of ten), right
  after the three throughput runs and two power cycles. Two more runs on the same boot: 4/4 both times, worst 599 ms and
  711 ms. One outlier in thirty injected faults; not reproduced and not explained. The reload itself passed in all three runs.

### The rpiboot entry (bench note)

The relay tool had sent IN1 (power) and IN2 (nRPIBOOT) in the same instant since 2026-11-12; sent that way one relay did not
pull in, and five entries failed on 2026-11-20 before the operator, listening at the bench, pointed at the order. With the
power off first and IN2 switched on a moment later the boot ROM enumerated every time. The tool and the runbook are corrected
in the same change as this update.
