# Metal evidence — 2026-11-14 evening (CM5 bench, fortress port-4)

All on the bench CM5. Images were built from main plus the named commits and installed by OTA
(`tools/diagnostics/cm5-ota-check.sh`, 9/9 each).

## 1. OTA to v0.0-26 needs the HBoot version pin (#1173)

- **Before:** a build of main after the release merge (#1163) was refused at upload:
  `finish: {"ok": false, "refused": "boot loader differs from the installed one (boot-loader updates are USB-only)"}`.
- **Cause:** the release aligned the `hboot` and `boot-abi` crate versions to 0.0.26. A crate's version feeds
  rustc's symbol mangling, so HBoot's bytes changed.
- **Fix:** with only those two crates back at 0.1.0, the rebuilt image's 2 MiB HBoot prefix is byte-identical to the
  installed one (`cmp`).
- **After:** OTA PASS 9/9 at 17:08, 17:52, 18:14 and 18:24. `release_check.py` enforces `BOOT_PIN`.

## 2. SEC-01 / ADR 0050 D4 step 5c on metal — station SAE frames are walked in EL0

Board on `rl1-78352069` (main). The Pi's wlan0 joined with WPA3-SAE after the 18:24 boot (`[WPA3] SAE … Committed`,
`… Accepted`). `GET /api/health` → `dns_parser`:

```
{'where': 'el0', 'el0_messages': 295, 'el0_faults': 1, 'el0_restarts': 1, 'in_kernel_messages': 0, 'sae_frames_el0': 8}
```

- `sae_frames_el0 = 8`: the station's Authentication frames went through `CMD_STA_SAE` in `el0-lansvc`.
- `in_kernel_messages = 0`: the in-kernel fallback never ran.
- The one EL0 fault and restart is the boot self-test's deliberate fault (`[P-lansvc]`).

Steps 1, 2a, 2b, 3, 5a, 5b and now 5c of SEC-01 are proven on metal. What remains is the authenticator state
machine, which moves with the driver and is not built yet.

## 3. A-04 — DNS to the AP refused after #1165, fixed by #1179

- **Found by the Pi session's DNS-01 repro:** from the AP client, `dig @10.99.0.1` → "host unreachable" while ping
  worked.
- **Cause:** #1165's refuse-local check matched the AP's own address (`is_local_ip` slot 0) before Shield could
  answer.
- **After #1179 (image dns2 / rl1):** Shield answers a benign name in under 2 s from the AP client.
- `[P-apcore]` now covers it: DNS to the AP is answered, and a packet to the management address is refused.

## 4. DNS-01 — the RX-before-TX hypothesis is disproved

- **Change tested (image dns2, never merged):** locally built replies were queued into the priority queue, so they
  leave in the drain step after the RX drain, instead of being sent directly.
- **Result:** the first blocked answer after boot was still held, more than 6 s (`dig +time=6`: no answer). The beat
  line shows the answer was queued and then drained normally (`prio queued=1 … pending=0`), so it entered the
  firmware after the RX drain and was held there anyway.
- **Status:** DNS-01 stays open. The one clue left is that a ~20 ms gap before the TX avoids it (MB20). The change
  was dropped.
