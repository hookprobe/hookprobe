## Open defect DNS-01 — the first blocked DNS answer per boot is held ~3 s

Pre-existing (reproduced on the known-good image `td` as well). Reproduced with relay power cycles (IN1 only) and a
capture on the Pi:

- After every CM5 boot (4/4, from 65 s to 250 s after boot) the **first blocked** lookup times out (3 s); the next one
  answers in 3 ms. The first **allowed** lookup after a boot answers normally (11 ms); a Pi rejoin without a CM5 reboot
  does not trigger it; Pi power save off does not change it.
- Capture: the held answer (id 44853) reached the Pi 3.35 s late, 0.1 ms before the answer to the next query — it was
  not lost, it went out with the next uplink frame. Shield counted it at once (`blocked=1` in the beat).
- Not owner enrollment (MB18), not TX credit (`credit=40`, `credit_refused=0`, no queueing: `prio queued=0`, `wq queued=0`).
- MB20 (diagnostic image `m20-dnsdiag`, branch `diag/shield-first-answer`, not for merge): `[SHIELD-ANS]` / `[DNS-TX]`
  lines show the answer built at once and sent on the direct path with credit, both queues empty, interface 0 — and with
  those serial prints (~20 ms before the send) **the defect did not occur** (all answers 19 ms).

Working hypothesis: the AP sends the locally built answer into the firmware within ~0.1 ms of reading the query, while
the firmware may still have RX pending (brcmfmac drains RX before pushing TX); the first such frame per boot is held
until the next uplink. Forwarded answers are never affected (they wait an upstream round trip). Candidate fix: locally
built replies go through the TX drain step (after the RX drain) instead of the direct send — a change on the hot Wi-Fi
TX path, so it needs its own metal run (throughput + this repro). Impact meanwhile: a client's first blocked lookup per
device boot waits for its resolver's retry (typically 1–3 s); the name stays blocked.

Nothing in this record marks a release gate complete.
