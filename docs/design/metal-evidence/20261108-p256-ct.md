# P-256 ECDSA signing — constant-time check (2026-11-08)

The device's Mission Control TLS key signs with p256 0.13.2 / ecdsa 0.16.9 (`tlsprov`, RFC 6979 nonces).
The "P-256 dudect run" was on the needs-the-board list; the same ctgrind method used for ML-KEM answers it on the
host: `os/build/kem-diff/ctgrind/p256` marks the private scalar UNDEFINED for valgrind memcheck, signs public
messages, and declares the signature defined.

Result: 30 reports = 10 sites x 3 signatures, **all validity-flag declassifications**, none on the arithmetic:

| Site | What branches |
|---|---|
| `subtle` `From<CtOption>` / `CtOption::unwrap` (lib.rs:663/701) via `SecretKey::from_bytes`, `generate_k`, `invert`, `ScalarPrimitive::from_slice` | the is-valid flag of a constant-time result |
| `SecretKey::from_bytes` (secret_key.rs:148) | scalar is in [1, n) |
| `rfc6979::generate_k` | candidate k in range (retry with probability ~2^-32) |
| `ecdsa::hazmat::sign_prehashed` (hazmat.rs:235) | `k.is_zero()` |
| `Signature::from_scalars` (lib.rs:254) | r and s non-zero |

Each reveals only a yes/no that is "yes" except with negligible probability — the standard, accepted
declassification. Scalar inversion, fixed-base multiplication k x G and the scalar arithmetic `k^-1 (z + r d)`
produce no reports: no branch or memory address depends on the key. Verdict: P-256 signing is constant-time for
the key as used by heqk; no change needed. (Not a CI gate: suppressing generic `CtOption` frames by name would
be too broad.)
