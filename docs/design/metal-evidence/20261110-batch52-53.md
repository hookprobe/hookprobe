## Guest SSID: this firmware cannot run a second AP
```
 [GUEST-PROBE] mbss get=true value=0 | set 1: ok=false bcme -23
 [GUEST-PROBE] on interface 1: bss op 3 (manual AP bsscfg create) ok=true bcme 0 | bss enable ok=false bcme -1
 [GUEST-PROBE] create bsscfg 1: ok=false bcme 0 | WLC_E_IF (ifidx, action, bsscfgidx, role) = None | bsscfg:wsec ok=true bcme 0 | bsscfg:wpa_auth ok=true bcme 0 | bss up ok=false bcme -1
 [GUEST-PROBE] mbss get=true value=0 | set 1: ok=false bcme -23
 [GUEST-PROBE] create bsscfg 1: ok=true bcme 0 | WLC_E_IF (ifidx, action, bsscfgidx, role) = Some((1, 1, 1, 1)) | bsscfg:wsec ok=true bcme 0 | bsscfg:wpa_auth ok=true bcme 0 | bss up ok=false bcme -1
```
- `mbss` reads 0 and cannot be enabled (BCME −23 UNSUPPORTED).
- `bsscfg:ssid` does create a BSS object (`WLC_E_IF` ADD, ifidx 1, role AP) and accepts its security.
- Bringing it up fails in both brcmfmac orders (`bss` enable → BCME −1; op 3 `MANUAL_AP_BSSCFG_CREATE` then enable → −1).

**A guest SSID needs a firmware build with MBSS (supplier dependency).** Guest-style isolation is already available on the main SSID through the per-device `internet_only` policy (parity G9).

## Cross-reference: brcmfmac interface-combination limits (operator note, 2026-11-10)

The operator confirmed the driver-level limits for this chip. They agree with the probe above:

- AP mode: yes, a single hotspot.
- STA mode: yes.
- AP + STA concurrently: yes, but locked to one shared channel.
- Two APs (a second SSID): **no**. The interface combination is `#{ AP } <= 1`, so adding a secondary BSS fails. The bench saw the same at the firmware level: the BSS object is created, but bringing it up returns −1, and `mbss` returns −23.
- 2.4 GHz and 5 GHz at once: **no**, the chip has one radio.
- Monitor mode: yes, but it typically tears down AP/STA.

Consequence: a guest SSID needs different firmware or hardware. On this chip, guest isolation is the per-device `internet_only` policy.
